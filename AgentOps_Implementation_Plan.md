# AgentOps platform and workspace plan

## Product direction

AgentOps is a workspace for operating AI employees across the services a company uses. The demo uses Mistral and a release review. A new workspace should be able to select a different model, connect different services, assign capabilities to its employees, and run a different workflow without changing the web app. The standalone Mastra service owns execution and remains usable with the web container stopped. Supabase and Docker remain the reference deployment.

## Agentic UI decision

Agentic UI is the interaction layer that turns the agent stream into chat, structured results, tool progress, and actions such as approvals. Mastra documents several client integrations.

| Integration | Fit |
| --- | --- |
| AI SDK UI | Adopt as the primary transport and message format. AgentOps already uses `@mastra/ai-sdk` and `useChat`. Use the native conversion for stream and history, and add tool-aware approval and artifact renderers around those parts. [AI SDK UI](https://mastra.ai/integrations/agentic-ui/ai-sdk-ui) |
| Assistant UI | Evaluate its chat primitives if they materially simplify keyboard interaction, accessibility, or thread navigation. Existing shadcn primitives already fit the current format. [Assistant UI](https://mastra.ai/integrations/agentic-ui/assistant-ui) |
| CopilotKit / AG-UI | Revisit for an embedded copilot that shares live page state and triggers UI-specific actions. The primary agent must also run headlessly. [CopilotKit](https://mastra.ai/integrations/agentic-ui/copilotkit) |
| OpenUI | Evaluate for generated forms or charts after identifying a concrete use case. Start with typed components for trusted tool results. [OpenUI](https://mastra.ai/integrations/agentic-ui/openui) |

## Implementation order and checkpoints

1. Establish provider discovery independently from invocation. Replace the tiny Settings provider directory with pinned SDK discovery, show actual supported operations and connection status, and ship Workflows template, run-list, and detail layouts using current native run data.
2. Add native account management and self-hosted MCP. Exercise a provider unknown to AgentOps and an alternate model profile using the headless API. Migrate saved model defaults and credentials. Enable new grants only after the native approval/resume path supports each entry point that exposes those grants.
3. Add native stored workflows and agent configuration. Prove two companies can independently publish and execute definitions with overlapping names. Complete the authoring and run inspection views. Cover suspend, restart, resume, and invalid references.
4. Apply the page designs to the rest of the workspace. Add native trace links and typed approval parts. Add knowledge, schedules, and supported channel installers using real data. Keep demos as seeded examples.
5. Verify optional runtime integrations independently. A connected service acceptance test reads data from a real provider and, when enabled, performs an explicitly approved write. A channel acceptance test delivers a reply with the web container stopped. Record required account plans and pin versions before advertising support.

## Search, schedules, and long-running execution

AgentOps exposes Tavily, Brave Search, and TinyFish as workspace-configured search providers. The search tool returns up to five bounded excerpts and source URLs. TinyFetch uses the same TinyFish credential and is a separate employee grant for reading public pages. Provider credentials remain server-side. [Tavily API](https://help.tavily.com/articles/4840311948-tavily-search-api) · [Brave API](https://api-dashboard.search.brave.com/documentation/quickstart) · [TinySearch](https://docs.tinyfish.ai/tinysearch) · [TinyFetch](https://docs.tinyfish.ai/tinyfetch)

The pinned Mastra Core and Postgres adapter provide native schedules. The scheduled-task workflow invokes the same assignment path as an interactive task. Completed scheduled release briefs enter the native suspend/resume human review flow. The self-hosted service must be running for scheduler workers to execute.

Keep Mastra as the backend framework. Treat Mastra Platform hosting and hosted integrations as separate operator choices. Prove Docker-equivalent data access, scheduling, channel ingress, and recovery before changing the reference deployment. The public console remains AgentOps.

Current employee runs use native subagents, bounded steps and deadlines, and bounded recent chat memory. Native schedule persistence and suspended review recovery do not make an individual model call restart-resumable. For long jobs, validate Mastra's beta Durable Agents against dynamic tenant-scoped rosters, Postgres fencing, native approval and resume, and restart during live work. Evaluate Observational Memory on the configured model with a long test thread and measure what context is retained. Preserve per-worker isolation and let the supervisor review completed results before final delivery. [Durable Agents](https://mastra.ai/docs/harness/durable-agents) · [Observational Memory](https://mastra.ai/learn/observational-memory)

### Background assignments and schedule controls

- The console submits ordinary tasks through an evented workflow and polls the company task record for status. The existing synchronous endpoint remains available. The asynchronous path extends the execution budget to five minutes and permits more team or tool steps. A worker claims a queued row atomically, and repeated request IDs return the original assignment.
- Workspace owners can pause or resume schedules, trigger an active recurrence on demand, and see its latest 15 native trigger records. A trigger records delivery to the execution engine. Task results and human decisions remain in Tasks and Workflows.
- The evented workflow addresses client disconnects. Restart recovery for in-flight model generation requires a separate durable-agent integration. Managed Connect channels require a Platform project and public ingress. Before enabling them, verify install routing and sender-to-company authorization for two distinct workspaces. Migrating the application host is optional. [Connect channels](https://mastra.ai/reference/connect/channels)
- The Docker smoke test received HTTP 202, resubmitted the same task ID, and observed the successful model result in a later request. A recurring schedule was paused, resumed, triggered manually, and inspected through the history endpoint. The temporary schedule was removed after the test.

## Panel, authority, and reliability

The workspace owner manages members, selects the team lead and roster, grants tools per employee, configures credentials, and decides workflow approvals. Workspace members can submit assignments under those grants. Leads coordinate work inside their team and cannot grant permissions. Each worker receives its own scoped tools and the assignment delegated to it. Use **Conversations → Set up Panel** to choose a lead and teammates. Demo setup supplies a sample roster through the authenticated API. With the web client offline, use `POST /agentops/v1/companies/:companyId/teams`, then send a `teamId` and prompt to `POST /agentops/v1/companies/:companyId/tasks/background`. The task and its delegations are available through the corresponding task read endpoints.

The Panel transcript displays recent team assignments. Turning a follow-up into a new assignment currently requires supplying context in the new request. A native shared team thread is the planned way to provide follow-up context. The lead uses native Mastra subagents and in-run result references for dependencies between workers. Time and model-step budgets bound execution. Text runs with tools reserve the last step to report results. Worker and lead instructions ask for evidence, uncertainty, and incomplete work. The database closes unfinished delegation records when the parent finishes. These controls bound ordinary execution and make failures visible. Provider errors, unsupported claims, and abrupt process termination remain possible.

## Conversation architecture review

Office and Conversations now present one workspace-owned conversation surface. The layouts share the same selection, per-thread drafts, and AI SDK state. Mastra Memory remains the durable source of private and channel conversations. Panel shows the team's persisted assignments and worker activity. Keep platform histories scoped to their linked senders. Neither a shared employee nor a compact layout changes a thread's audience.

The service discovers linked channel threads without retrieving their messages. Only the open thread refreshes its history. History responses that started before a local send cannot replace the streaming transcript. A short PostgreSQL transaction claims each reply across the streaming API, JSON API, and channel entry points. The transaction ends before model or tool execution. The activity row provides a bounded claim and diagnostics. Console model errors preserve run IDs while omitting raw provider error payloads.

The rest of the review identified changes that need separate acceptance tests.

| Area | Design decision and acceptance check |
| --- | --- |
| Task and run history | Panel currently uses the latest 100 workspace assignments. Add team-filtered cursor pagination when older history is needed. Share task identity across Panel, Tasks, and Workflows, and verify a busy team cannot push another team's history out of view. |
| Durable delivery | Background task insertion and workflow dispatch are separate operations. Verify recovery from a crash between them before promising automatic recovery. Keep PostgreSQL as the task record and native workflows as the execution record. Verify replay and expired claims with two service replicas. |
| Channel configuration | Workspace-managed channels and the legacy environment-configured Telegram path coexist. Define and test an installation and thread migration before retiring the legacy path. Verify sender, installation, and workspace isolation for both routes. |
| Provider credentials | Settings keep credentials server-side and write-only in the API. Database columns still contain usable secrets. Move them to a managed secret store or encrypt them with a separately managed key. Verify rotation, restored backups, and compatibility with existing connections. |

## Context and company knowledge

Direct and channel conversations keep the latest 20 Mastra messages for recall, scoped to the thread and authorized user or sender. The transcript API can return up to 50 stored messages. The demo model also uses a 24,000-token input limiter. Ordinary tasks, scheduled runs, and team assignments start from their task input. A lead passes relevant findings to workers through delegation and task results. Earlier private conversations remain in their own threads. [Mastra Memory](https://mastra.ai/docs/memory/overview)

The headless service owns upload authorization and document storage. It validates one bounded upload, extracts PDF text by page when needed, and uses pinned `@mastra/rag` `MDocument` to split text into overlapping excerpts of up to 900 characters. One PostgreSQL transaction indexes all excerpts and creates the source record. A repeated upload of the same normalized text and page layout returns the existing source. Sources and excerpts share the company ID, with a composite foreign key and cascading deletion. The database stores indexed text and provenance. The original binary is discarded. [MDocument](https://mastra.ai/reference/rag/document) · [unpdf](https://github.com/unjs/unpdf)

The read-only `company-knowledge` tool is bound by the service to the authorized company and exposed by employee tool grants. Manual preview and agents share the same ranked PostgreSQL full-text retrieval. Each invocation returns at most four excerpts. Each chat reply or assignment has a budget of two searches across its lead and workers, for up to 7,200 characters of retrieved excerpt text. The budget bounds material introduced from the index. Model input billing can still include earlier steps or worker messages. Tool results carry filename, page when available, and excerpt number. Instructions tell agents to treat excerpts as reference data and cite them. Persisted chat tool parts keep citation metadata and discard raw excerpts. Generated answers and saved task results can still quote documents. Native trace input and output are hidden on chat runs and knowledge-enabled task agents.

Mastra Knowledge provides a graph of pages and notes with scopes and optional pinned context. Its current alpha and importer model are a better fit for a separate evaluation around agent-maintained notes. The upload pipeline uses native chunking with the existing PostgreSQL deployment. Keyword retrieval suits policy names, acronyms, and exact terms and incurs no separate embedding or reranking charges. If a representative evaluation shows misses on paraphrases or multilingual corpora, add hybrid retrieval behind the same API using Mastra PgVector with per-company filters, an explicit embedding model and dimension, and versioned reindexing. Distinct from document retrieval, Mastra Observational Memory can compress longer conversations using extra model calls. Evaluate it with an explicitly configured model, per-tenant credentials, cost ceilings, and tests for old facts and deletions before enabling it. [Knowledge](https://mastra.ai/docs/knowledge/overview) · [PgVector](https://mastra.ai/integrations/vectors/pg) · [Observational Memory](https://mastra.ai/docs/memory/observational-memory)

Deploy after applying `db/012-knowledge.sql` through the standard migration runner. Verify with `node --experimental-transform-types scripts/test-knowledge.mjs` against a migrated disposable PostgreSQL database. It exercises two companies, owner authorization, duplicate upload, PDF citations, bounded tool use, saved chat tool parts, and deletion. A release smoke test should also upload a document in the deployed console and ask a configured employee to cite it in a chat and a team task.
